## Budget and deployment

The shared application ceiling is $9.50/month in usage, before credits. FlightAware currently publishes $0.05 per regional search result set and $0.005 per airport board result set (up to 15 records/set). Verify account-specific pricing and feeder credit in the AeroAPI portal. Other applications using the key are outside this local ledger.

Four regional pages after 12 UTC daily plus two pages per direction for five airports once at 04:00 America/New_York cost at most $9.30 in a 31-day month at these rates. The 04:00–04:00 service window follows local daylight-saving time. Each board contains at most 30 flights and is explicitly partial. Airport clicks only read the shared database; they never call FlightAware. The worker wakes every 15 minutes and durable reservation windows suppress duplicates across restarts. Failed requests retain their maximum reservation; no unaccounted automatic retries occur. The ledger locks across processes, writes atomically and fails closed on corruption or save failure. Never delete it mid-month. Legacy query counts migrate at the conservative $0.05/page rate; reconcile against portal month-to-date usage before enabling polling. Missing successful windows in an old ledger may cause a first refresh, charged against the remaining balance.

## Morning board rollout and inference

Deploy migration `20261104180000_airport_boards.sql`, compatible web readers, then the new worker. The FlightAware worker now invokes only the morning collector and daily regional snapshot; the previous six-hour MIA path is no longer invoked. Keep the same ledger so month-to-date usage remains counted. Each airport/date/direction/attempt reserves two pages before HTTP. Failure retains that reservation and leaves old boards intact. There is no automatic paid retry; the next service day is a fresh window. The collector uses ICAO airport identifiers for FlightAware and IATA identifiers for internal boards. Review portal usage during the transition month; the $9.50 cap can stop collection early if older polling has already used its allowance.

Baselines retain seven days and flight progress cascades on baseline deletion. Official fields remain immutable between provider downloads. Observed progress uses only recent receiver observations matched to normalized callsigns, compatible scheduled endpoints, and a -3h/+12h flight window. Ambiguous matches and registration conflicts are ignored. Two observations 15–180 seconds apart are required. Approach needs sustained descent below 3,000 ft toward the airport within 20km. Likely landing requires earlier approach evidence within ten minutes and two ground samples within 3km, with no closer neighboring field. Departure needs a ground-to-climb transition near the origin. Reception gaps reset movement evidence; missed reception never implies arrival or cancellation. Movement evidence warms up again after process restart; persisted observed events remain visible with their timestamp. Five minutes without observations changes the UI to “Last observation.” No exact touchdown, gate, cancellation, or ETA inference is published. Airports beyond antenna coverage may have no observed progress.

Acceptance evidence must record the actual deployed SHA, migration version, portal month-to-date usage, morning baseline timestamps for all five airports, receiver heartbeat/history timestamps over 30–60 minutes, bounded track log growth, and delivered failure/recovery notifications. These are production checks, not claims made by local tests. Run receiver-only model evaluations after sufficient history; hardware photos and range plots must be real observations. Do not apply MIA models to other airports without evaluation.
